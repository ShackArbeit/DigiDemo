# Demo 3 解說筆記：MyData 授權流程概念模擬

> ⚠️ **這是「概念模擬」，不是 MyData 的真實規格或介面。** 資料表設計、欄位名稱、流程都是為了面試展示而簡化的版本。

## 3-A：資料模型與資料庫（`demo3/db.py`）

### 資料表關聯
```
                 ┌──────────────────────┐
                 │ citizens（民眾）       │
                 │ PK citizen_id         │
                 │    national_id, name… │
                 └──────────┬───────────┘
          1 ┌───────────────┼────────────────┐ 1
            │               │ 1              │
            ▼ N             ▼ N              ▼ N
┌───────────────────┐ ┌──────────────────┐ ┌───────────────────────┐
│ land_records       │ │ consents（同意）  │ │ audit_log（稽核日誌）  │
│ （地政機關持有）    │ │ PK consent_id     │ │ PK log_id              │
│ PK record_id       │ │ FK citizen_id     │ │ FK citizen_id（資料主體）│
│ FK citizen_id      │ │ client_id/name    │ │ FK consent_id（可為空）  │
│ 地號、地址、持分、  │ │ purpose, scopes   │◀┤ actor, action          │
│ 面積、公告現值…     │ │ created/expires   │1 N requested_fields     │
└───────────────────┘ │ status            │ │ result, prev_hash, hash│
                      └──────────────────┘ └───────────────────────┘
```
- 一位民眾可以有多筆不動產、多份同意、多筆稽核紀錄。
- 一份同意可以對應多筆稽核紀錄（例如銀行憑同一份同意存取了 3 次）。
- `consents.scopes` 存的是 `land_records` 的**欄位名稱**，這是「欄位最小化」的依據。
- `audit_log` 每筆的 `prev_hash` 指向前一筆的 `hash`，串成一條鏈（3-B 實作）。

### 每張表的用途與對應的法遵原則

#### 1. `citizens`（民眾）
- **用途**：資料主體，也就是「這些資料是誰的」。
- **欄位**：內部編號 `citizen_id`、身分證字號、姓名、性別、生日、手機。
- **對應原則：當事人權利**。所有授權和稽核紀錄都綁定到資料主體，民眾才能行使查詢、撤回等權利。
- **設計重點**：主鍵用內部編號 C001，**不用身分證字號**。身分證字號如果當作主鍵，就會被複製到其他每一張表，擴大個資外洩的範圍。這是**資料最小化**在系統設計上的實踐。

#### 2. `land_records`（地政機關持有的資料）
- **用途**：模擬「資料提供機關」持有的民眾資料。
- **8 個欄位**：地號、房屋地址、權利範圍（持分）、建物面積、公告土地現值、登記日期、登記原因、他項權利（抵押權）。
- **對應原則：最小必要原則**。每個欄位都可以單獨授權。銀行辦房貸需要地址、持分、面積、公告現值、抵押權；但**登記原因**（例如繼承、贈與、拍賣）透露家庭與財務狀況，房貸審核通常不需要。3-C 的「越權請求」情境就是銀行要求未授權的「登記原因」。
- **主角王小明有兩筆不動產**：大安區一筆單獨所有（持分 1/1），文山區一筆與他人共有（持分 1/2），可以展示持分欄位的意義。

#### 3. `consents`（同意紀錄）
- **用途**：記錄「誰、授權給誰、為了什麼用途、可以拿哪些欄位、到什麼時候」。
- **欄位與對應原則**：

  | 欄位 | 意義 | 對應原則 |
  |---|---|---|
  | `citizen_id` | 誰同意 | 告知後同意：同意必須由當事人本人做出 |
  | `client_id`、`client_name` | 授權給誰 | 告知後同意：要清楚告知資料給了誰 |
  | `purpose` | 用途 | **特定目的**：個資法要求蒐集、利用都要有特定目的 |
  | `scopes` | 可存取的欄位 | **最小必要**：只授權該目的需要的欄位 |
  | `expires_at` | 效期 | **期限限制**：目的達成後就不應繼續存取 |
  | `status`、`revoked_at` | 有效或已撤回 | **可撤回性**：民眾可以隨時撤回同意 |

- **設計重點**：
  - `status` 只有 `active`（有效）和 `revoked`（已撤回）兩種，由資料庫的 CHECK 條件強制。「**過期**」不另外存成狀態，而是每次存取時**比對 `expires_at` 和現在的時間**。這樣不需要排程程式定時更新狀態，也不會有「已經過期但狀態還沒更新」的空窗期。
  - 撤回時**不刪除**同意紀錄，只把狀態改成 `revoked` 並記錄撤回時間。這樣事後仍然可以查到「這份同意在什麼期間有效」，對問責很重要。
  - `scopes` 用 JSON 陣列存成一個文字欄位。正規化的作法是另開一張表，但對 demo 來說，一個欄位比較容易看懂。

#### 4. `audit_log`（稽核日誌）
- **用途**：記錄每一次操作，**不論成功或失敗**：建立同意、撤回、換取令牌、存取資料、查詢日誌。
- **欄位**：時間、操作者（actor）、動作（action）、資料主體（citizen_id）、依據的同意（consent_id）、請求的欄位、結果（allowed / denied）、補充說明（例如拒絕原因）、`prev_hash`、`hash`。
- **對應原則：可問責性（accountability）**，以及民眾的**查詢權**。
  - 民眾可以用 `citizen_id` 查詢「誰在什麼時候、為了什麼目的，拿了我的哪些資料」。
  - 失敗的請求也要記錄：越權請求被擋下，本身就是重要的稽核線索（這個第三方在嘗試拿不該拿的資料）。
- **設計重點**：
  - 比 PROMPTS.md 要求的欄位多了 `citizen_id` 和 `detail`。`citizen_id` 讓民眾查詢自己的紀錄時不必繞經 consents 表；`detail` 用來記錄拒絕原因（越權、撤回、過期）。
  - `prev_hash` / `hash` 讓日誌**無法被悄悄竄改**（3-B 實作）。

### 重建資料庫
```powershell
.venv\Scripts\python.exe -m demo3.db
```
- 產生 `data/mydata.db`：民眾 21 筆、地政資料 23 筆，同意和日誌是空的。
- 每次執行都會**清空重建**，假資料用固定 seed，所以結果都一樣。錄影前執行一次，就能回到乾淨的初始狀態。
- `*.db` 已加入 `.gitignore`。

### 假資料（`shared/fake_data.py` 的 `generate_citizens`）
- 王小明的姓名、性別、生日固定（1985-03-15），身分證字號由產生器產生，保證檢查碼正確。
- 其他 20 位民眾用 `Faker('zh_TW')` 產生，姓名和性別一致，每人 0～2 筆不動產。
- 地址重用 Demo 1 的臺北市 5 區道路；地號的段名從固定清單中隨機挑選；公告土地現值每平方公尺 15～120 萬元。

### 測試（`tests/test_db.py`）
- 四張表都存在；地政資料至少 6 個欄位；稽核日誌有 hash chain 所需的欄位。
- 21 位民眾、C001 是王小明、所有身分證字號都通過檢查碼。
- 外鍵有效（不能為不存在的民眾新增地政資料）；同意狀態只能是 active / revoked。

### 限制（面試可能被追問）
- **真實的 MyData 不是這樣運作的**：真實的 MyData 平台會串接各機關既有的系統，機關不會把資料集中到同一個資料庫。這裡把四張表放在一個 SQLite 檔，只是為了方便展示。
- 第三方（銀行）沒有獨立的資料表，只存在同意紀錄的 `client_id` 和 `client_name` 中。實務上，第三方要先經過申請、審核、簽約才能介接，應該有獨立的管理表。
- 身分驗證（例如自然人憑證、行動身分識別）不在本 demo 的範圍內，這裡假設民眾已經完成身分驗證。
- SQLite 適合單機 demo，不適合多人同時寫入的正式環境。

## 3-B：稽核日誌 hash chain（`demo3/api/audit.py`）

### 先懂 hash（雜湊）
- **hash 是資料的「數位指紋」**：任何資料丟進 SHA-256，都會得到一串固定 64 個字元的值。
- 三個特性：
  1. **同樣的內容，永遠得到同樣的 hash。**
  2. **內容只要改一個字，hash 就完全不同**（測試裡把 `denied` 改成 `Denied`，hash 就整串改變）。
  3. **無法從 hash 反推原始內容**，也幾乎不可能找到兩份內容不同、hash 卻相同的資料。

### hash chain 的原理（白話版）
> 每一筆日誌除了記錄自己的內容，還會**抄下前一筆的指紋**，然後把「前一筆的指紋＋自己的內容」一起算出自己的指紋。
>
> ```
> 第 1 筆：hash₁ = SHA-256( 000…000 + 內容₁ )
> 第 2 筆：hash₂ = SHA-256( hash₁    + 內容₂ )
> 第 3 筆：hash₃ = SHA-256( hash₂    + 內容₃ )
> ```
>
> 所以每一筆都和前一筆**扣在一起**。

**為什麼改不了？** 假設有人想把第 3 筆的「越權被拒」改成「允許」，掩蓋這次越權：
1. 他只改內容 → 第 3 筆重算的 hash 和儲存的 hash₃ 對不上 → **抓到，第 3 筆內容被改**。
2. 他連 hash₃ 一起重算 → 第 4 筆抄下的「前一筆指紋」還是舊的 hash₃ → **抓到，第 4 筆的 prev_hash 對不上**。
3. 他要完全不被發現，就必須把第 3 筆**之後的每一筆**都重算一次。而只要外部保存過任何一個較新的 hash（見下方限制），這樣做也會被發現。

**一句話**：「**改一筆，就要改掉後面全部；而後面的每一筆，都是證人。**」

### 它在做什麼
| 函式 | 用途 |
|---|---|
| `compute_hash(prev_hash, record)` | 計算 SHA-256(prev_hash + 本筆內容) |
| `append_log(conn, actor, action, result, …)` | 新增一筆紀錄，自動接到鏈尾；**只能新增，不提供修改或刪除** |
| `verify_chain(conn)` | 從第一筆開始逐筆驗證，回傳是否完整、**第幾筆**出問題、原因 |
| `tamper_log_for_demo(conn, log_id, 欄位, 值)` | ⚠️ 僅供展示：繞過正常流程直接改資料庫，用來示範竄改會被偵測 |

### 設計細節
- **第一筆的 prev_hash 是 64 個 0**（創世值），鏈才有固定的起點。
- **內容先轉成「固定格式」的 JSON 再計算**（欄位順序固定、中文不轉碼、沒有多餘空白）。否則同樣的內容如果排列順序不同，就會算出不同的 hash，造成誤報。
- **log_id 也納入 hash 計算**：調換順序或重新編號都會被發現。
- **每筆檢查兩件事**：
  1. `prev_hash` 是否等於前一筆的 hash → 可以偵測刪除、插入、調換順序、連 hash 一起改。
  2. 重算的 hash 是否等於儲存的 hash → 可以偵測內容被修改。
- **回報第一個出問題的位置**：從那一筆開始，之後的紀錄都不再可信。

### 測試（`tests/test_audit.py`）
- 第一筆接到創世值；每一筆的 prev_hash 都等於前一筆的 hash。
- 同樣內容得到同樣的 hash；改一個字 hash 就不同。
- 空的日誌、完整的日誌都通過驗證。
- **竄改中間一筆**（第 4 筆的 denied 改成 allowed）→ 偵測出第 4 筆，原因是內容被修改。
- **竄改並重算 hash**（第 3 筆）→ 偵測出第 4 筆，原因是 prev_hash 不一致。
- **刪除中間一筆**（第 2 筆）→ 偵測出原本的第 3 筆。
- 驗證之後再新增紀錄，鏈仍然完整。

### 為什麼這對「可問責性」很重要
- **可問責性的前提是紀錄可信。** 如果日誌可以被悄悄修改，「誰拿了我的資料」這個問題就沒有可信的答案。民眾的查詢權、機關的內部稽核、事後的調查，全部都會落空。
- **最需要防的往往是內部人員**：有權限碰到資料庫的人，正是最有能力修改日誌、掩蓋不當存取的人。hash chain 讓**連系統管理者都無法悄悄改紀錄**，任何修改都會留下痕跡。
- **把「相信我」變成「你可以自己驗證」**：機關不需要說「請相信我們沒改過日誌」，而是提供一個任何人都能執行的驗證方法。這是跨機關資料流通時建立信任的基礎：資料提供機關、第三方、民眾彼此不必完全互信，也能確認紀錄沒有被動過。
- 對應個資法和《促進資料創新利用發展條例》草案的精神：資料可以流通，但每一次流通都要**留下可信、可查證的軌跡**。

### 連結數位鑑識的「證物監管鏈」（chain of custody）
> 給 Shack 的備選說法（擇一使用，也可以自己調整）：
>
> 1. **「我在高檢署管理數位鑑識實驗室時，每一件證物都要有監管鏈：誰在什麼時間經手、做了什麼，每次交接都要記錄。只要有一個環節說不清楚，證據在法庭上就會被質疑。hash chain 就是把同樣的精神放進資料系統：每一次存取都留下紀錄，而且每一筆都和前一筆扣在一起。」**
> 2. **「在數位鑑識裡，我們製作證物映像檔時，第一件事就是計算 hash 值，證明之後分析的資料和原始證物一模一樣。這個 demo 把同樣的方法用在稽核日誌上，不同的是，它把每一筆紀錄的 hash 串成一條鏈。」**
> 3. （短版，適合放在簡報上）**「證物要有監管鏈，個資的每一次流通也要有。」**
>
> 建議：說法 1 用在 Demo 3 情境 5 的旁白；說法 3 放在簡報標題；說法 2 留著回答追問（例如「hash 真的可靠嗎？」），因為它能展現你實際使用過 hash 驗證證物。

### 限制（面試可能被追問）
- **刪除最後幾筆無法單靠鏈本身偵測**：如果有人刪掉鏈尾的紀錄，剩下的鏈仍然是完整的。
  - 解法：定期把**最新的 hash 存放到外部**，例如寄給獨立的稽核單位、寫入只能寫不能改的儲存設備（WORM），或使用時間戳記服務。之後只要比對外部保存的 hash，就能確認日誌沒有被截斷。
- **擁有資料庫完整權限的人，可以把整條鏈全部重算**：同樣靠「外部錨定」解決。只要外部保存過任何一個 hash，重算後的鏈就會和它對不上。
- **hash chain 只能「偵測」竄改，不能「防止」竄改**：防止要靠權限控管、職務分離（管理系統的人不能管理日誌）。兩者要搭配使用。
- **這不是區塊鏈**：區塊鏈是讓「多個彼此不信任的單位」共同維護同一份帳本，需要共識機制，成本高。這裡只有一個機關寫日誌，hash chain 加上外部錨定就能達到防竄改的目的，簡單很多。（3-E 會再整理成追問的回答。）
- `append_log` 先讀取最後一筆、再寫入新紀錄。如果多個請求同時寫入，可能讓兩筆接到同一個前一筆。demo 是單人操作所以沒有問題，正式環境要用資料庫鎖或交易來確保寫入順序。

## 3-C：FastAPI 後端（`demo3/api/`）

### 啟動
```powershell
$env:MYDATA_JWT_SECRET = "請換成一串夠長的隨機字串"
.venv\Scripts\uvicorn.exe demo3.api.main:app --port 8000
```
- API 文件（可以直接在網頁上試打）：http://localhost:8000/docs
- 沒有設定 `MYDATA_JWT_SECRET` 時，會自動產生一把臨時密鑰並顯示警告。

### 檔案分工
| 檔案 | 內容 |
|---|---|
| `main.py` | 建立 FastAPI app，掛上各模組的路由 |
| `deps.py` | 共用設定：資料庫連線、JWT 密鑰、**唯一的時鐘** `now()`、已註冊的第三方 |
| `consent.py` | 建立同意、撤回同意、判斷同意是否有效 |
| `tokens.py` | 簽發與驗證 JWT |
| `provider.py` | 資料提供機關（地政機關）提供資料 |
| `audit.py` | hash chain 核心邏輯（3-B） |

| `demo.py` | ⚠️ 僅供展示：重設、時鐘快轉、竄改日誌 |

`deps.py`、`audit_routes.py`、`demo.py` 是 CLAUDE.md 結構之外多出的檔案：前兩個是為了避免模組互相引用造成循環，`demo.py` 是 3-D 錄影需要的展示功能。

### API 一覽
| API | 誰呼叫 | 做什麼 |
|---|---|---|
| `POST /consents` | 民眾 | 建立同意：授權給誰、用途、可存取欄位（scopes）、效期（天） |
| `POST /consents/{id}/revoke` | 民眾 | 撤回同意（只有本人可以撤回） |
| `POST /token` | 第三方 | 用「自己的帳號密碼」＋「consent_id」換取 JWT |
| `GET /provider/land-records/{citizen_id}?fields=…` | 第三方 | 憑 JWT 向地政機關取資料 |
| `GET /citizens/{id}/access-log` | 民眾 | 查詢誰在什麼時候、為了什麼、拿了哪些資料 |
| `GET /audit/verify` | 任何人 | 驗證日誌是否完整 |
| `POST /demo/reset`、`/demo/advance-clock`、`/demo/tamper` | 展示用 | 重設、時鐘快轉、竄改日誌 |

### 整體流程
```
 民眾 ──① POST /consents（同意）──────────▶ 系統：寫入 consents ＋ 日誌
 銀行 ──② POST /token（帳密＋consent_id）─▶ 系統：檢查同意 → 簽發 JWT（15 分鐘）
 銀行 ──③ GET /provider/…（帶 JWT）──────▶ 地政機關：五道檢查 → 只回傳授權欄位
 民眾 ──④ POST /consents/{id}/revoke ─────▶ 狀態改為 revoked → 下一次 ③ 立即被拒
 民眾 ──⑤ GET /citizens/{id}/access-log ──▶ 看到 ①～④ 每一步的紀錄
```

### 機關端的五道檢查（`provider.py`，**每一次請求都重新檢查**）
| 順序 | 檢查 | 失敗時 | 對應原則 |
|---|---|---|---|
| 1 | 令牌簽章是否有效 | 401 | 防止偽造、竄改令牌 |
| 2 | 令牌是否屬於這位民眾 | 403 | 不能拿 A 的授權查 B 的資料 |
| 3 | **重新查資料庫**：同意是否已撤回或過期 | 403 | **可撤回性**、期限限制 |
| 4 | 令牌是否過期 | 401 | 降低令牌被偷的風險 |
| 5 | 請求的欄位是否都在授權範圍內 | 403 | **最小必要** |

- 全部通過後，SQL 只 `SELECT` 請求的欄位，**未授權的欄位連讀都不讀**，更不會回傳。
- **不論成功或失敗都寫入稽核日誌**，失敗時會記下拒絕原因。

### JWT 是什麼（白話版）
- JWT 是一張「**數位通行證**」：上面寫著「示範銀行可以在 15 分鐘內，依同意 CNS-0001 取得王小明的這 5 個欄位」，並由系統用密鑰**簽名**。
- 內容任何人都看得到（只是編碼，不是加密），但**沒有密鑰就改不了、也偽造不了**：銀行把 scopes 偷偷加上「登記原因」，簽名就會對不上（測試 `test_missing_or_forged_token_rejected`）。
- 本 demo 的令牌內容：`sub`（第三方）、`consent_id`、`citizen_id`、`scopes`、`iat`（簽發時間）、`exp`（到期時間）、`jti`（令牌編號）。

### 設計重點（面試很可能被問）
1. **為什麼有了令牌，每次還要重新查資料庫？**
   令牌一旦簽發出去，系統就收不回來。如果機關只看令牌，民眾撤回之後，銀行手上的令牌在到期前還是能用。**每次都重新查同意狀態，撤回才能「即時」生效。**這是本 demo 最核心的設計（情境 3）。
2. **令牌只有 15 分鐘，而且不會比同意活得更久**：到期時間取「15 分鐘後」和「同意到期時間」中較早的那個。令牌被偷，能被濫用的時間也很短。
3. **「過期」和「撤回」的訊息分開**：機關先檢查同意狀態，再檢查令牌是否過期，所以情境 4 會清楚顯示「同意已過期（到期時間…）」，而不是籠統的「令牌過期」。兩項檢查都會做，順序只影響顯示的原因。
4. **整個系統只有一個時鐘**（`deps.now()`）：同意的效期、令牌的到期、日誌的時間都用它。情境 4 用「時鐘快轉 31 天」示範過期，對所有檢查都同時生效。也因為這樣，JWT 的到期時間由程式自己用這個時鐘檢查，而不是交給 pyjwt。
5. **第三方要用自己的帳密換令牌**：光有 consent_id 不夠。保險公司拿到銀行的 consent_id 也換不到令牌（`test_other_client_cannot_use_consent`）。帳密比對使用 `secrets.compare_digest`，避免攻擊者從比對所花的時間猜出密碼。
6. **民眾查詢日誌本身也會被記錄**（`log.view`），符合「每一次存取都要記錄」。

### JWT 密鑰的管理
- **demo**：從環境變數 `MYDATA_JWT_SECRET` 讀取，**不寫在程式碼裡**（程式碼會進版本控制，任何看得到程式碼的人都會知道密鑰）。測試用的密鑰寫在 `tests/conftest.py`，只用於測試。
- **正式環境應該**（寫在 `deps.py` 的註解中）：
  1. 把密鑰放在**金鑰管理服務**（雲端 KMS、HashiCorp Vault、硬體安全模組 HSM），由系統啟動時注入。
  2. **定期輪替**，並保留舊密鑰一段時間，讓尚未過期的令牌仍可驗證。
  3. 改用**非對稱簽章**（RS256 / ES256）：只有授權伺服器有私鑰、負責簽發，各資料提供機關只拿公鑰驗證。**就算某個機關被入侵，攻擊者也無法偽造令牌。**這在多機關介接的架構特別重要。

### 測試（`tests/test_api.py`，共 17 個）
| 情境 | 驗證內容 |
|---|---|
| 1 正常流程 | 取得 2 筆資料，只有請求的欄位；不指定欄位時只回傳授權的 5 個欄位；令牌內含 consent_id、scopes、exp |
| 2 越權請求 | 請求「登記原因」→ 403，日誌記下被拒與請求的欄位 |
| 3 撤回授權 | 撤回後，同一個令牌立即被拒（403）；也無法換新令牌；非本人不能撤回 |
| 4 過期 | 時鐘快轉 31 天 → 403「同意已過期」；同意還在但令牌超過 15 分鐘 → 401 |
| 5 存取紀錄＋完整性 | 日誌依序記錄 6 個動作；竄改第 4 筆後，驗證回報第 4 筆 |
| 其他 | 錯誤帳密、別的第三方冒用、偽造令牌、拿 A 的令牌查 B、不存在的欄位、重設功能 |

### 限制（面試可能被追問）
- **身分驗證不在範圍內**：API 直接相信請求中的 `citizen_id`。真實的 MyData 要求民眾先用自然人憑證、行動身分識別等方式驗證身分。
- **第三方帳密寫在程式碼中**（`deps.CLIENTS`）：只是 demo。正式環境要有第三方的申請、審核、簽約流程，帳密要加密保存。
- 機關端會先查自己的資料庫中的同意紀錄。真實架構中，資料提供機關和同意管理系統通常是**不同單位**，機關要回頭向同意管理系統查詢狀態（例如 OAuth 2.0 的 Token Introspection），這會增加網路延遲，是「即時撤回」和「效能」之間的取捨。
- 沒有限制查詢頻率、沒有使用 HTTPS（本機 demo）。正式環境都必須要有。

### 每個情境三個角色看到什麼
| 情境 | 👤 民眾 | 🏛️ 地政機關 | 🏦 銀行 |
|---|---|---|---|
| 1 正常 | 同意內容（對象、用途、效期）＋可存取欄位標籤（綠✓／紅✗） | 收到的請求 → 五道檢查全 ✓ → 「回傳 4 欄，其餘 4 欄不讀取」→ 寫入日誌 #n 與 hash | 取得令牌（顯示令牌內容）→ 取得 2 筆資料表格 |

### 設計細節
- **介面透過 HTTP 呼叫 FastAPI**，不是直接讀資料庫：民眾、機關、銀行看到的都是 API 實際回傳的結果，介面上的每個 ✓／✗ 都是後端真的檢查出來的。

- **地政機關欄的五道檢查**：依後端回傳的拒絕原因，標出是第幾道失敗、之後的檢查顯示「未執行」。
- **銀行欄顯示的令牌內容只是解碼**（JWT 的內容本來就看得到），不驗證簽章，驗證是機關端的工作。
- 新增 `GET /audit/logs`（唯讀，不寫日誌）給 hash chain 表使用。如果改用民眾的查詢 API，每次畫面更新都會多一筆「查詢紀錄」，日誌會越來越亂。

## 評審可能追問的問題與建議回答

### Q1：真實的 MyData 怎麼做身分驗證？你的 demo 為什麼沒有？
- **回答方向**：
  - 真實的 MyData 要求民眾在授權前先驗證身分，常見的方式包括自然人憑證、行動自然人憑證、健保卡加註冊密碼、晶片金融卡等（**面試前請到 MyData 官網確認目前支援的方式**）。
  - 這個 demo 刻意把身分驗證放在範圍外，因為我想聚焦在「驗證身分**之後**」的授權控管：給誰、給哪些欄位、給多久、能不能收回、事後查不查得到。
  - 身分驗證決定「**你是誰**」，授權控管決定「**你可以做什麼**」，兩者缺一不可。在介接輔導時，這兩件事也要分開檢核。
- **加分說法**：「身分驗證的強度應該和資料的敏感程度相稱。查詢公開資訊和取得不動產資料，需要的驗證強度不一樣。」

### Q2：JWT 令牌被偷了怎麼辦？
- **回答方向**：這個 demo 用了**三層**防護：
  1. **令牌壽命很短**：只有 15 分鐘，而且不會超過同意的效期。被偷走，能被濫用的時間也很短。
  2. **每次存取都重新檢查同意**：民眾發現異常、按下撤回，被偷的令牌立刻失效，不用等它過期。
  3. **每次存取都留下紀錄**：異常存取（例如不尋常的時間、頻率）事後查得到，民眾自己也看得到。
- **正式環境還可以加上**：
  - 令牌**綁定第三方的身分**，例如用雙向 TLS 憑證，讓偷到令牌的人沒有對應的憑證就無法使用。
  - 全程 HTTPS、限制查詢頻率、異常行為偵測。
  - 密鑰放在金鑰管理服務，並改用非對稱簽章，讓各機關只持有公鑰，就算某個機關被入侵也無法偽造令牌。
- **一句話**：「令牌是通行證，但**真正的授權依據是資料庫裡的同意紀錄**，民眾隨時可以收回。」

### Q3：為什麼不用區塊鏈？
- **回答方向**：
  - 區塊鏈要解決的是「**多個彼此不信任的單位**，要共同維護同一份帳本」，代價是共識機制、效能和維運成本。
  - 這裡的需求是「**日誌不能被悄悄竄改**」，hash chain 就能做到：改一筆，後面就全部對不上。再加上**定期把最新的 hash 存放到外部**（交給獨立的稽核單位、寫入只能寫不能改的儲存設備，或使用時間戳記服務），連有最高權限的管理者重算整條鏈也會被發現。
  - 區塊鏈底層用的其實也是 hash chain。差別在於要不要多方共同記帳。
  - 另外，**個資不適合上區塊鏈**：區塊鏈的資料難以刪除，和個資法的刪除權、更正權互相衝突。
- **一句話**：「技術選擇要看要解決的問題。防竄改用 hash chain 加外部錨定就夠，不需要為了新技術付出區塊鏈的成本。」
- **連結經歷**：數位鑑識實務上，證物完整性也是靠 hash 值加上監管紀錄來證明，並不需要區塊鏈。

### Q4：每次存取都要回頭查同意狀態，跨機關時效能會不會有問題？
- **回答方向**：
  - 這是「**即時撤回**」和「**效能**」之間的取捨，需要依資料的敏感程度決定，而不是一律採用同一種做法。
  - 真實架構中，資料提供機關和同意管理系統通常是不同單位。機關可以在每次存取時，向同意管理系統查詢令牌是否仍有效（業界標準做法如 OAuth 2.0 的 Token Introspection）。
  - 可以調整的地方：
    - **令牌壽命**：越短，撤回生效越快，但換發越頻繁。
    - **短時間快取**：例如快取同意狀態 1 分鐘，可以降低查詢次數，代價是撤回最多延遲 1 分鐘生效。
    - **主動通知**：民眾撤回時，同意管理系統主動通知相關機關。
  - 高敏感資料（例如病歷、不動產）應該每次都即時檢查；低敏感資料可以接受較短的延遲。
- **一句話**：「撤回要多即時，是一個需要在介接規範中**明文訂定**的服務水準，不應該由各機關自己決定。」

### Q5：民眾真的看得懂要授權哪些欄位嗎？會不會變成「看都不看就按同意」？
- **回答方向**：這是「告知後同意」最常見的問題（同意疲勞），技術上可以做到，但更需要**制度設計**：
  1. **用途綁定欄位**：由第三方事先申請「房貸審核需要哪些欄位」，經過審查，而不是讓第三方臨時要什麼就勾什麼。民眾看到的是一個合理的組合，而不是一長串選項。
  2. **白話說明**：每個欄位附上「這會透露什麼」，例如「登記原因：會顯示這筆不動產是買來的、繼承的或受贈的」。
  3. **預設最小**：預設只勾選必要欄位，額外的欄位需要民眾主動勾選。
  4. **事後透明**：就算當下沒仔細看，事後也能查到每一次存取紀錄，並且隨時撤回。這正是情境 3 和 5 的意義。
- **一句話**：「好的同意機制不是讓民眾讀更多條款，而是**讓第三方只能要合理的東西**，並且讓民眾事後查得到、收得回。」

### 備用：如果被問「你怎麼輔導機關介接」
- 把 demo 的五個情境轉成**介接檢核清單**：
  1. 欄位是否已分級，scope 是否和用途對應（最小必要）？
  2. 機關端是否每次存取都檢查同意狀態，而不是只驗證令牌（可撤回性）？
  3. 同意的效期和到期處理方式是否明確（期限限制）？
  4. 越權和失敗的請求是否也有記錄（可問責性）？
  5. 稽核日誌是否防竄改，是否有外部保存機制？民眾能否查詢自己的紀錄（當事人權利）？
- 對非技術背景的機關同仁，用「**這五個情境，你們的系統能不能做到？**」來溝通，比直接談技術規格更容易推動。

## 效能修正：切換情境很慢（2026-11-06）

**症狀**：每次點擊情境都要等 7～22 秒。

**原因**（實測，每次 API 請求的耗時）：
| 連線方式 | 耗時 |
|---|---|
| `localhost`＋每次建立新連線（原本的寫法） | 約 2,600 ms |
| `127.0.0.1`＋每次建立新連線 | 約 740 ms |
| 共用同一條連線 | 約 5 ms |

1. **Windows 上的 `localhost` 會先嘗試 IPv6（`::1`）**，但 uvicorn 只監聽 IPv4，每次都要等 IPv6 連線失敗才改用 IPv4，多花約 2 秒。
2. **每次呼叫都重新建立 httpx 連線**，光建立連線就要幾百毫秒。
3. 一個情境要呼叫 API 5～10 次（建立同意、換令牌、取資料、讀日誌……），延遲就疊加成十幾秒。

**修法**（`demo3/app.py`）：
- 後端網址預設改為 `http://127.0.0.1:8000`。
- 用 `st.cache_resource` 讓整個介面**共用一條 HTTP 連線**。
- 健康檢查改用 2 秒的短逾時，後端沒開時畫面不會卡住。

**結果**：
| 操作 | 修正前 | 修正後 |
|---|---|---|
| 情境 1 | 12.8 秒 | 0.18 秒 |
| 情境 4 | 22.1 秒 | 0.23 秒 |
| 重設 | 8.6 秒 | 0.22 秒 |

**面試可以怎麼講**（如果被問到開發過程遇到的問題）：「一開始切換情境要等十幾秒。我實際量測後發現不是程式邏輯的問題，而是每次請求都重新建立連線，加上 Windows 解析 localhost 的方式多了 2 秒延遲。改成共用連線後，速度提升了將近百倍。這也提醒我，跨機關介接的效能問題常常出在連線層，不一定在系統本身。」

## Bug 修正：正常流程出現「✗ 1. 令牌簽章有效」（2026-11-06）

**症狀**：先跑情境 4，沒有按重設就跑情境 1，地政機關欄的第 1 道檢查顯示 ✗，銀行拿不到資料。

**原因**：
- 情境 4 把系統時鐘快轉 31 天，新令牌的簽發時間（`iat`）因此是 31 天後的日期。
- 驗證令牌時，我已經關掉 pyjwt 的到期時間（`exp`）檢查，改用系統唯一的時鐘，但**漏掉了簽發時間（`iat`）**。pyjwt 用電腦的**真實時間**檢查，認為令牌「還沒生效」（`ImmatureSignatureError`）。
- 原本的程式把所有令牌錯誤都歸類成「簽章錯誤或格式不符」，所以畫面也顯示成簽章問題，**錯誤訊息誤導了排查方向**。

**修法**：
1. `tokens.py`：pyjwt 只負責驗證簽章，所有時間檢查（`exp`、`iat`、`nbf`）都關掉，統一由系統時鐘判斷。
2. `provider.py`：錯誤訊息依實際原因區分：「簽章錯誤（令牌被竄改或偽造）」「格式不符」「簽發時間在未來」。簽發時間的檢查改用系統時鐘，容許 60 秒誤差。
3. 新增兩個測試：快轉時鐘後跑正常流程仍要成功；竄改簽章、亂打令牌時，錯誤訊息要正確。

**學到的事**（面試可以用）：
- **系統中所有和時間有關的判斷，都要用同一個時鐘。** 混用兩個時鐘，就會出現「這邊說有效、那邊說還沒生效」的矛盾。跨機關介接時也一樣：各機關伺服器的時間如果不同步，令牌的有效期判斷就會出錯，所以實務上會容許幾十秒的誤差，並要求各機關校時。
- **錯誤訊息要具體。** 籠統的錯誤訊息會讓人往錯的方向排查。在介接輔導時，清楚的錯誤代碼和訊息，可以大幅減少機關之間來回確認的時間。
